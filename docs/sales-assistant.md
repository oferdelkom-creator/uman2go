# Sales assistant infrastructure

The assistant is embedded in the homepage opening section and also available at `/assistant`. Admin inbox: `/admin/ai-conversations`. The shared desktop and mobile navigation links to the assistant in all four site languages. Desktop navigation uses its own row to keep all links accessible without crowding the account controls.

Onboarding first asks for a name locally, then phone OR email and explicit storage/summary-email consent. The saved session opens the sales conversation. The finish button freezes the conversation, creates a Hebrew AI handoff (with a clearly labelled transcript fallback), saves it, and sends plain-text email using the existing Resend integration to `ofer.delkom@gmail.com`. Only server constants determine the recipient. The summary covers the request, dates, group size, budget, discussed suggestions, open questions, follow-up and information requiring verification. It never automatically changes catalogue facts. Contact details are kept out of the summarization prompt.

Completion shares the atomic conversation lock with chat generation. Finished sessions cannot accept new chat turns. Email acceptance and summary are saved in the admin inbox. A stable Resend idempotency key prevents duplicate submissions within the provider's 24-hour window; unknown/failed delivery retries are limited to 23 hours from completion. Missing credentials or rejected email are shown as failure, with the lead and summary retained. Acceptance by Resend is not proof of inbox delivery. A visitor can finish immediately. Otherwise Supabase Cron checks once a minute and automatically completes conversations after five minutes without a new sent message/reply, including after browser closure. A new message/reply resets updated_at. The idle claim locks and rechecks that timestamp to prevent a stale selection from closing an active conversation. Automatic delivery retries are limited to three attempts, five minutes apart, inside the same 23-hour deduplication window. The browser polls completion state every 30 seconds while a conversation is open. The mailbox copy is outside the site's 30-day cleanup.

Live schema addition: `supabase/sales-assistant-completion.sql`. Completion security, locking, immutable chat and deduplication-window regression: `supabase/tests/sales-assistant-completion.sql` (rolled back).

Uses the existing server-side `ANTHROPIC_API_KEY`, with AI SDK 7 and `@ai-sdk/anthropic`. The default model is the newest Haiku returned by the authenticated Anthropic Models API. Set `SALES_ASSISTANT_MODEL` to a valid Anthropic model to override discovery. Set `SALES_ASSISTANT_ENABLED=false` to disable session creation and generation. Missing credentials fail closed. `SUPABASE_SERVICE_ROLE_KEY` stays on the server; preview environments without it do not process customer conversations. Failure diagnostics contain only the processing stage and HTTP status, never credentials or customer content.

Name and phone OR email, plus explicit consent, are stored before chatting. Contact data is not sent to the model. Conversation content is sent to Anthropic as disclosed in the form. Only a random HttpOnly, Secure-in-production, SameSite Strict cookie is retained in the browser. Its SHA-256 digest identifies the conversation server-side. No customer details are put into localStorage or application logs. Resume is limited to the same browser and 30-day session lifetime. A shared browser can expose its own resumed conversation; use "start a new conversation" before another customer uses it.

The model receives bounded public active listings for accommodation, transport, guides and upcoming organized tours. It cannot change bookings, take payments, contact suppliers or send customer messages. Published terms govern each tour; payment goes directly to the organizer. Missing data and custom quotes require a human representative. Replies are rendered as text, with links restricted to site routes and the official WhatsApp contact.

User messages persist before provider calls, so interrupted or failed generations leave the enquiry available to the admin. The admin overview is an extract of the customer's recent messages, not an AI interpretation. Full transcripts are available. Only administrators can read contacts or messages; browser roles cannot write these tables or read session-token hashes.

Atomic daily quotas: 8 starts/IP, 150 starts/site, 60 calls/IP, 300 calls/site, 40 turns/session. One generation per session is allowed, with a 90-second lock recovery window. Model history uses the last 12 messages, each user input is capped at 2,000 characters, output at 700 tokens, retries disabled and generation time capped at 40 seconds. IP values are stored only as keyed digests. These are usage limits rather than a monetary budget.

Schema reference: `supabase/sales-assistant-schema.sql`. Live migrations are applied through Supabase; do not replay them on the existing database. Security and quota verification: `supabase/tests/sales-assistant.sql`, transactional with no retained fixtures.

Expired conversations cannot be resumed or read through the admin page. The `uman-sales-retention` database job deletes expired conversations and their messages hourly; physical deletion happens within one hour after the 30-day expiry, even without visitor traffic. Old quota counters are deleted too. The session creation route also removes expired records.

Idle scheduling: `supabase/sales-assistant-idle.sql` and `supabase/tests/sales-assistant-idle.sql`. `uman-sales-idle-summary` invokes a private dispatcher every minute, only when work is due; it calls the production-only `/api/internal/sales-summary` endpoint. A dedicated `SALES_SUMMARY_CRON_SECRET` is stored as a Vercel Secret and in Supabase Vault (`uman_sales_summary_cron_token`), never in repository files or logs. Requests and responses contain no contact details. Each invocation handles at most three conversations concurrently. The existing email sender and fixed owner recipient remain unchanged.

Scheduler requests use a signed timestamp and random nonce, accepted for 90 seconds and consumed once using an atomic quota. The persistent signing secret never enters the pg_net request queue. Both Vault and dispatcher remain private.

The assistant also identifies provider onboarding intent, asks about category/business/service area/capacity and desired listing, and points to the verified /join hub. It does not approve or publish providers or invent commercial terms. Handoff summaries distinguish traveler enquiries, provider applications, mixed intent and unclear intent; provider summaries include service details and missing information for review.
